# PhotoTok — Requirements

> Product: **PhotoTok** (`products/android/phototok/`, Gradle module `:phototok`, package
> `com.phototok`). Target: phone form factor (< 600 dp), portrait, gesture-first.
> Scope: this file is authoritative for the PhotoTok app only. PhotoTok deliberately
> excludes OpenCV analysis, the Room score cache and Vico charts to stay lightweight —
> see [`../../shared/FEATURE_PARITY.md`](../../shared/FEATURE_PARITY.md).
> Android platform baseline: [`../../shared/ANDROID_PLATFORM.md`](../../shared/ANDROID_PLATFORM.md).
> Visual design: [`DESIGN.md`](DESIGN.md). Architecture: [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 1. Feature Set & Exclusions

PhotoTok may additionally omit:
*   **[REQ-TOK-FEATURE.01] Focus Mode Exclusion:** Focus Mode / side-by-side comparison view (not practical on small screens).
*   **[REQ-TOK-FEATURE.02] Detailed EXIF Panel Exclusion:** Detailed EXIF metadata panel (accessible via tap-to-expand on phone).

*   **[REQ-TOK-FEATURE.03] First-Time User Experience & Start Page Options:** On launch (`PhoneModeLanding`), users are offered two primary source options: "Phone Camera" (navigates directly into the device camera roll) and "Custom Folder" (launches the SAF tree picker). Selecting either source navigates directly into the feed / loading screen without requiring a secondary confirmation tap (eliminating the "Start Browsing" double-gate). A "Resume [Folder]" card is only displayed when an active session with photos already exists.
*   **[REQ-TOK-FEATURE.04] Empty Folder State:** When a selected folder contains 0 supported photos, an explanatory warning card is displayed on the landing page ("No supported photos found in [Folder]"), preventing silent reload loops and clearly prompting the user to choose another folder.
*   **[REQ-TOK-FEATURE.05] Default Selection Folder & Root Option:** The default collection destination folder is named `"Selection"` (`PhotoFolders.SELECTION`). By default, it is placed in a centralized location independent of the scanned folder. A setting ("Store Selection in Scanned Folder", `selectionUseSourceRoot`) allows placing the `Selection` folder inside the scanned folder. Custom target folders remain supported.
*   **[REQ-TOK-FEATURE.06] Selection View Affordance:** The viewer bottom bar and landscape side panel display a `CollectionsBookmark` icon labelled "Selection" (rather than a misleading Star icon) to clearly distinguish viewing the selection folder from a per-photo favorite toggle. When the selection folder is empty or uninitialized, an informative message is shown without error styling (`isError = false`).
*   **[REQ-TOK-FEATURE.07] EXIF Metadata Info Button:** Both portrait top app bar and landscape side panel include a prominent `(i)` Info button (`Icons.Default.Info`, `testTag("info_exif_button")` and `testTag("landscape_info_exif_button")`) to toggle camera/EXIF metadata directly alongside the tap-to-expand logo gesture.
*   **[REQ-TOK-FEATURE.08] Feed Ordering & Unscanned Photo Navigation:** Default feed order is strictly chronological by last-modified time ascending (`it.lastModified` ascending, tie-breaking by filename). Batches maintain this order as photos stream in, and when enumeration completes, non-randomized feeds perform a full chronological re-sort while preserving the user's active photo by URI. When opening a folder outside an active session, if new photos are detected that were not yet scanned (photos newer than the previous session's recorded maximum timestamp), PhotoTok navigates directly to the first new unscanned photo in the chronological feed so the user sees the newest files first; if no new photos exist, it restores the last-viewed position.
*   **[REQ-TOK-FEATURE.09] Folder Reload & Active Session Refresh:** An in-app Reload button in the top app bar, landscape side panel, and Settings triggers an immediate folder rescan from disk. During an active review session, reloading preserves the currently viewed photo; if new photos are discovered, a centered modal dialog (`AlertDialog`) informs the user of the new photo count and offers them the choice to stay at the current photo or jump to the latest photos. If no new photos are found, feedback is shown and the current photo position is maintained.
*   **[REQ-TOK-FEATURE.10] Picture Randomization:** A toggle in settings allows users to randomize the order of pictures shown in the viewer. Enabling this setting shuffles the loaded pictures and overrides orientation-based sorting.
*   **[REQ-TOK-FEATURE.11] RAW + JPEG Pair Suggestion:** When browsing a folder containing matching RAW and JPEG pairs of the same pictures, the app presents a centered, non-occluded suggestion dialog (`RawJpegSuggestionDialog` / `RawJpegSuggestionCard`) giving users clear, understandable options to: (1) link actions across both formats (`moveRelatedFiles = true`) so move, copy, and delete apply to both files at once, (2) filter the feed to view only RAW photos (`FileTypeFilter.RAW`), (3) filter the feed to view only JPEG photos (`FileTypeFilter.JPG`), or (4) don't change settings, keeping all files visible and separate without modifying preferences. The dialog is rendered in a dedicated dialog window to prevent occlusion by bottom action bars (favorites and folder symbols) or landscape side panels across all devices and orientations. Interacting with any choice or dismissing the dialog marks the `raw_jpeg_pairs` hint as seen.

## 2. Gesture & Touch Interaction

*   **[REQ-TOK-GESTURE.01] Vertical Navigation & Action Swipes:** Vertical swipe via `VerticalPager` (up/down) to navigate between images in the feed, and horizontal swipe gestures for the configured copy/move/delete actions.
*   **[REQ-TOK-GESTURE.02] Zoom & Pan Gestures:**
      - Pinch-to-zoom (two fingers) and double-tap zoom (to 2.5x) are supported.
      - Zoom gesture detection is decoupled from zoom threshold state (`pointerInput(Unit)`) so that crossing the zoomed threshold (`scale > 1.05f`) does not tear down or reset the active pointer stream mid-pinch.
      - When zoomed in (`scale > 1.05f`), dragging with a single finger pans/moves the image frame, constrained within image boundaries so it does not go off-screen.
      - While zoomed, normal swipe gestures (vertical paging scroll and horizontal keep/discard swipes) and navigation peeks are disabled to prevent conflicts and visual edge artifacts.
      - Image containers apply strict bounds clipping (`Modifier.clipToBounds()`), ensuring scaled images in portrait or landscape orientations never bleed beyond their viewports (preventing edge tint stripes or overlapping side panel controls).
      - Resetting zoom (double-tapping again, or pinch-releasing below the `1.05f` threshold) smoothly animates the scale and offset back to fit-screen size and re-enables swiping mode.
*   **[REQ-TOK-GESTURE.03] Selection/Deletion & Direct Delete Confirmation:** Long-press for context menu. Swipe gestures configurable. On PhotoTok, swiping left defaults to a non-blocking temporary deletion where the image is immediately hidden from the viewer and a "Revert Deletion" button is shown. Vertical scrolling between remaining photos does not prematurely finalize the deletion; the undo affordance remains available across scrolls. Exiting the viewer, selecting a new folder, or performing another destructive operation finalizes the deletion and deletes the file via SAF. Before putting the image into the temporary deletion state, the **Direct Delete Confirmation** dialog is shown. It does not have a checkbox in the dialog, but hints that it can be disabled in settings. In settings, this **Direct Delete Confirmation** option is offered with a warning indication.
    - The revert option is preserved immediately after confirmation.
    Alternatively, in settings, the user can configure a different behavior for the left swipe: Copy to Custom Folder or Move to Custom Folder, matching the behavior of the right swipe. When configured as Copy or Move, the operation is executed immediately (showing a success feedback message and an action icon flash animation) and targets a user-defined folder. If no custom folder is selected, it defaults to a subfolder named `"PhotoTok_LeftSwipe"` inside the source folder.
*   **[REQ-TOK-GESTURE.04] Non-Blocking Copy/Move:** A copy or move must never make the user wait on file I/O. The feed is updated **optimistically the moment the gesture completes** — a move drops the photo (and its included siblings) out of the feed, a copy advances to the next photo — and the transfer then runs on the injected application-scoped `CoroutineScope` (`@ApplicationScope`) so it also completes if the user leaves the screen immediately after swiping. Because the feed is ahead of the file system, failure handling is mandatory: any file that did **not** actually move is re-inserted at its original position in both the filtered and unfiltered lists, and the failure is reported as error feedback. The re-insertion tracks the active photo by URI (`com.phototok.domain.OptimisticFeed`), never by index, so restoring a photo cannot silently shift the user onto a different one. A failed *copy* leaves the feed alone — the source file never left. The `ViewerBottomBar` "Revert" affordance continues to cover deletions only.
    For other clients or operations, delete uses Snackbar with Undo (30s) or confirmation dialogs.
*   **[REQ-TOK-GESTURE.05] First-Run Action Explanations:** Because the phone client is gesture-first, the *effect* of an action is invisible unless stated. The first time the user performs each action (swipe right, swipe left in either delete or copy/move mode, single tap, double tap, first vertical page change, first revert) or when loading a folder where the active file type filter hides the majority of unique photos (`FILTER_MISMATCH`), the app shows a dismissible explanation card describing what just happened and pointing at the relevant setting — e.g. "You copied this photo to Keepers. Every swipe right does the same. You can change this in Settings." or "Showing RAW photos only. Most photos in this folder are JPEG and are hidden. You can switch to All or change this in Settings." (providing a "SHOW ALL" action to immediately switch `FileTypeFilter.ALL`). Folders with matching RAW+JPEG pairs of the same pictures do not trigger the mismatch hint since both formats represent the same shots. Each explanation fires once; the seen-keys are persisted in DataStore (`seen_first_run_hints`). Wording is produced by the pure `com.phototok.domain.FirstRunHintText` from the user's *current* settings, so it always reflects the configured verb (copy vs. move) and the configured target folder. Explanations are suppressed while the full-screen tutorial is visible, and auto-dismiss after 7 seconds.
*   **[REQ-TOK-GESTURE.06] Swipe Indicator Labels:** The mid-swipe indicator must name the action the user has *configured*, never a default or a euphemism. Swipe right is labelled `COPY` or `MOVE` from `CollectionAction` (it must never read "KEEP" — the photo is filed into the collection folder, and under `MOVE` it leaves the source folder entirely); swipe left is labelled `COPY`, `MOVE` or `DELETE` from `SwipeAction`. Icons match the label (copy / move / trash) in the mid-swipe indicator, the post-action flash and the first-run idle "peek" hints, and the accessibility description names the destination folder. All of this wording lives in the pure `com.phototok.domain.SwipeLabels` so the viewer, the peeks and the controls guide cannot drift apart.
*   **[REQ-TOK-GESTURE.07] Controls Guide:** A help button in the viewer (portrait top app bar and landscape left side panel) toggles a **coach-mark overlay**, not a list. It dims the viewer and labels the controls where they actually are: callouts with short leader lines sit directly under the top app bar (logo → camera info, help, settings) and directly above the bottom bar (Sources, Selection, Revert), while the centre animates the three swipe directions — up/down for paging, left and right captioned with the configured actions and target folders — around a photo-shaped frame that carries the single-tap and double-tap/pinch hints. Everything fits on one screen: the guide must not scroll. It must not claim controls that do not exist (there is no camera symbol; the EXIF overlay is toggled by tapping the app logo), and it is parameterised by the configured swipe actions and folder names so it can never describe a left swipe as "delete" when the user has configured copy or move. The same composable serves the first-launch tutorial. The tutorial triggers on first launch, or automatically when the app has not been opened for 7 or more consecutive days (`now - lastAppUsedTs > ONE_WEEK_MS`). A "Reset Tutorials" entry in Settings clears the seen-hint keys and the tutorial timestamp so all guidance reappears.
*   **[REQ-TOK-GESTURE.08] Gesture Tutorial Overlay:** The overlay reserves the height of the real top app bar and bottom bar (`TOP_BAR_HEIGHT` / `BOTTOM_BAR_HEIGHT` in `GestureTutorialOverlay.kt`, kept in sync with `PhoneModeScreen` and `ViewerBottomBar`) and the bars therefore stay visible above the scrim — the coach marks exist to label those buttons, so hiding them would defeat the guide. The background scrim uses alpha `0.70f` to stay translucent rather than an overly dark mask, and top bar action icons/logo are dimmed to alpha `0.4f` while the guide or tutorial is shown so they do not compete with the coach marks. Top bar coach marks for Help and Settings omit duplicate internal icon glyphs (`icon = null`) to prevent visual clutter directly underneath the real app bar buttons. Nothing may overlap: the callouts sit inside the reserved bands, and the dismiss button sits above the bottom callouts. The overlay container must apply status bar and navigation bar padding to prevent clipping by system decorations. The first-run explanation cards remain suppressed while the overlay is visible.

## 3. Architecture Conventions

*   **[REQ-TOK-ARCH.01] Default Collection Folder Compatibility:** The default collection destination folder is named `"Selection"` (`PhotoFolders.SELECTION`), matching Desktop and Android Desktop conventions. Subfolder scanning automatically excludes `Selection`, `Selected`, `PhotoTok_Selection`, and `PhotoTok_LeftSwipe` case-insensitively, ensuring seamless cross-product compatibility when sharing the same storage or SD cards.
*   **[REQ-TOK-ARCH.02] Typed Settings:** User-facing choice settings are typed enums in `com.phototok.domain` (`SwipeAction` delete/copy/move, `CollectionAction` copy/move, `FileTypeFilter` all/raw/jpg). Raw strings must not be passed through ViewModels or UI; the DataStore wire format is the enum's `key` (backward compatible with previously persisted values).
*   **[REQ-TOK-ARCH.03] Typed Settings Flow:** All simple phone-mode settings are exposed by `SettingsRepository` as one typed flow (`phoneSettings: Flow<PhoneSettings>`) mapped from the single DataStore `Preferences` snapshot. ViewModels must collect this flow instead of `combine`-ing individual setting flows with positional array casts.
*   **[REQ-TOK-ARCH.04] Image Source Abstraction:** Every image backend implements `com.phototok.data.source.ImageSource` (currently only `LocalImageSourceImpl` for SAF/DocumentFile; SAF document providers also cover cloud storage such as Google Drive, so no dedicated remote backend exists). URI-scheme dispatch for per-image operations happens exclusively in `ImageSourceResolver`/`ImageRepositoryImpl`; ViewModels and UI must not branch on URI schemes. Cross-source copy/move is rejected by the repository. Adding a new backend means one new `ImageSource` implementation plus registration in the resolver.
*   **[REQ-TOK-ARCH.05] ViewModel Boundaries:** ViewModels must not hold `Context` or data-source clients. Folder-name resolution and permission persistence go through `ImageRepository.prepareSourceFolder`/`resolveFolderName`. The read-only selection viewer is backed by its own `SelectionViewerViewModel` (listing via `ImageRepository.listSelectionImages`).
*   **[REQ-TOK-ARCH.06] Pure Domain Logic:** List/ordering logic must live in `com.phototok.domain` free of Android dependencies so it is unit-testable: `PhoneFeedOrdering` (ordering, file-type filtering, portrait-split computation, progressive batch de-duplication and append), `PendingDeleteLogic` (pending-delete/revert list transitions), `OptimisticFeed` (recording feed slots and re-inserting files whose copy/move failed), `RelatedFiles` (sibling detection, RAW+JPEG pairing, and file-filter mismatch detection), `PhotoExtensions` (single source of truth for RAW/JPEG extension sets), `PhotoFolders` (app-managed folder names), `CopyMoveFeedback` (copy/move feedback messages incl. partial failures), `SwipeLabels` (swipe indicator and coach-mark wording).
*   **[REQ-TOK-ARCH.07] Scoped Sibling Matching:** Related file discovery (`RelatedFiles`) enforces that candidate sibling files share the exact same parent directory (`parentUri`) and have complementary extensions (`candidateExt != targetExt`), preventing accidental cross-directory pairing or matching files of identical extensions.
*   **[REQ-TOK-ARCH.08] Pending Deletion Lifecycle:** Finalizing a pending deletion (primary image AND its related siblings) must run on the injected application-scoped `CoroutineScope` (`@ApplicationScope`), never on an ad-hoc scope, so deletions complete even when the ViewModel is cleared mid-undo-window.
*   **[REQ-TOK-ARCH.09] Folder Discovery Lifecycle:** Only one image-discovery collection may be active at a time; selecting a new source folder cancels the previous discovery `Job` (and the dimension-loading `Job`) and clears the published-URI set and the current feed, so batches from a new folder cannot be appended to a stale one.
*   **[REQ-TOK-ARCH.10] Progressive Folder Discovery (time-to-first-swipe):** `ImageSource.discoverImages` must emit **progressively**, not once at the end: a first batch after `LocalImageSourceImpl.FIRST_BATCH_SIZE` (24) photos, then every `BATCH_SIZE` (250), then a final complete snapshot. Emissions are cumulative. Opening a folder with thousands of photos must therefore let the user swipe within a fraction of a second, with the viewer replacing the loading screen on the first batch and `PhoneModeUiState.isDiscovering` telling the UI the count is still growing (rendered as a trailing `+` on the page counter).
    - **[REQ-TOK-ARCH.11] One query per directory:** the walk is an iterative breadth-first traversal driven by `ContentResolver.query` on `DocumentsContract.buildChildDocumentsUriUsingTree`, selecting document id, display name, MIME type, size and last-modified in a single cursor per folder. `DocumentFile.listFiles()` plus its per-attribute getters must not be used for enumeration: each attribute is a separate binder round-trip (~5 per file), which is what made large folders take tens of seconds. A single unreadable directory is logged and skipped, never fatal.
    - **[REQ-TOK-ARCH.12] Append-only merge:** the ViewModel merges each batch with `PhoneFeedOrdering.newItems` (de-duplicate against every URI ever published for this folder, so a photo the user already moved or deleted is not resurrected) and `PhoneFeedOrdering.appendBatch` (order/shuffle the new batch only and append it). The already-visible feed must never be reordered mid-load. With randomization on this means the feed is shuffled per batch rather than globally — an accepted trade-off, since photos moving under the user's thumb is worse.
    - **[REQ-TOK-ARCH.13] Deferred position restore:** a saved per-folder position beyond the loaded range is clamped to what is available and re-applied as further batches arrive, until it is reached or the user changes page themselves (which cancels the restore).
    - **[REQ-TOK-ARCH.14] Dimension loading:** the dimension pass is not cancelled and restarted per batch; a run already in flight is left alone and each URI is read at most once, with a final forced pass when enumeration completes.
*   **[REQ-TOK-ARCH.15] File Copies:** A failed copy must not leave a zero-byte or partially written destination file behind.
*   **[REQ-TOK-ARCH.16] Copy/Move Feedback:** Copy/move actions track each file's result individually: only successfully moved files stay out of the feed (see **Non-Blocking Copy/Move** in §7.4 — removal is optimistic and reversed on failure), and partial failures are reported ("Moved 1 of 2 …, 1 failed") as error feedback.
*   **[REQ-TOK-ARCH.17] State Update Batching:** Asynchronously loaded image dimensions are applied to the UI state in batches (`PhoneModeViewModel.DIMENSION_BATCH_SIZE`), not per image, to bound recompositions in large folders.
*   **[REQ-TOK-ARCH.18] Per-Folder Positions & Scan Metadata:** Last-viewed positions are stored under URI-keyed preferences (`folder_pos_v2_<uri>`; legacy `hashCode`-based keys are read as fallback and cleaned up on write). Folder scan metadata (`folder_scan_time_v1_<uri>` for max last-modified timestamp and `folder_scan_count_v1_<uri>` for file count) is tracked per folder URI. When a folder is evicted from the recents list or caches are cleared, both its stored position and scan metadata are removed so the preferences file does not grow unboundedly.
*   **[REQ-TOK-ARCH.19] No Dedicated Cloud Integration (SAF ONLY):** PhotoTok must not integrate cloud storage SDKs or APIs directly (no Google Sign-In, no Drive REST client, no Google Picker, no OAuth scopes). Cloud storage is reached exclusively through the Storage Access Framework: the system folder picker (`ACTION_OPEN_DOCUMENT_TREE`) exposes cloud document providers (e.g. Google Drive) alongside local storage, and the resulting tree URIs behave like any other SAF source. Rationale: a generic single code path, no restricted-scope verification / CASA assessment, no GMS dependency, and no `INTERNET` permission — the app performs no network I/O of its own.
*   **[REQ-TOK-ARCH.20] Legal Links (Play compliance):** The settings screen must expose "Privacy Policy" and "Legal Notice (Impressum)" links (Google Play requires an in-app privacy-policy link; the Impressum addresses § 5 DDG). The public URLs live in `com.phototok.domain.LegalLinks` (single source of truth); the documents themselves are maintained in `docs/products/phototok/` and hosted publicly (see `docs/products/phototok/RELEASE_CHECKLIST.md`). The privacy policy documents the on-device processing model and must be updated when it changes.
